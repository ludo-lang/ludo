# Survey of the languages this one has to beat

**Research ticket:** [adamico/ludo#2](https://github.com/adamico/ludo/issues/2) · **Serves:** [#1](https://github.com/adamico/ludo/issues/1) · **Date of evidence:** 2026-07-24

Ten languages, judged against the destination in #1: a standalone, compiled, statically-typed systems language for game development with Lua's syntactic simplicity, Rust/Odin/C++-grade robustness, layered for beginners and veterans, and explicitly friendly to AI agents. Three lenses apply throughout — **simplicity** (would a Lua user recognise this?), **robustness** (does it catch a bug class at compile time?), **agent-friendliness** (can an LLM write it correctly without seeing the rest of the codebase?). The survey is deliberately unkind: the useful output is not a list of features to copy but a map of ground that is already occupied, plus the handful of problems nobody has solved. Where the evidence is thin, anecdotal, or vendor-supplied, it is labelled as such inline — that happens more often than is comfortable, especially for Jai, Beef and C3, where the honest finding is *there is no evidence*.

Two cross-cutting facts frame everything below.

**Corpus size is measurable and brutally skewed.** Public repository counts from the GitHub search API, measured 2026-07-24 (`gh api search/repositories -f q='language:X'`; counts depend on GitHub Linguist classification and should be treated as order-of-magnitude, not exact — the `Jai` and `C3` counts in particular are likely contaminated by unrelated repos):

| Language | Repos | Language | Repos |
|---|---:|---|---:|
| JavaScript | 45,942,784 | Zig | 35,752 |
| TypeScript | 17,196,162 | Luau | 12,362 |
| Ruby | 2,963,682 | Odin | 7,191 |
| Rust | 1,266,183 | Jai | 562 (unreliable) |
| Lua | 706,758 | Beef | 395 |
| Nim | 13,403 | C3 | 327 (unreliable) |
| | | Teal | 43 |

That is five orders of magnitude between JavaScript and Teal. GitHub's own Octoverse 2025 puts TypeScript at #1 by contributors — "August 2025 marks the first time TypeScript emerged as the most used language on GitHub, surpassing Python by ~42k contributors", with "over 1 million contributors in 2025 (+66% YoY)" — and names Luau the fastest-growing language by percentage at ">194%" growth, but on a base of just ">3,600 developers" ([GitHub Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/)). Fastest-growing and negligible are not contradictory.

**A new language starts at zero corpus, and that gap does not close by fine-tuning.** The most directly relevant experiment is *Syntax Without Semantics: Teaching Large Language Models to Code in an Unseen Language* ([arXiv:2605.15607](https://arxiv.org/html/2605.15607v1)), which built **PyLang**, a minimal language deliberately absent from all pretraining data, and measured frontier models on 352 problems with parallel Python solutions. Claude Sonnet 4.5 scored **58% on PyLang versus 88% on Python** — a 30-point deficit. A fine-tuned Qwen 32B reached 47% vs 64% — still a 17-point gap. Multi-task learning, preference tuning (DPO/GRPO), infilling and latent-space objectives all failed to close it. Crucially, the failure was *not* reasoning: models picked the same algorithm in PyLang as in Python 80% of the time, and "75% of failures involve the correct algorithm with buggy implementation". The one intervention that worked was **code snippets demonstrating correct idioms in context — worth 24 percentage points for Sonnet 4.5**, far more than stating rules.

The design consequence is sharp and it recurs in every section below: for a new language, agent-friendliness is not something you get from popularity. It comes from (a) idiom-dense, in-context documentation, (b) a compiler whose errors are precise enough to close the loop, and (c) **not changing**. Separately, type systems help mechanically: type-constrained decoding on TypeScript "reduces compilation errors by more than half" and "significantly increases functional correctness" ([arXiv:2504.09246](https://arxiv.org/abs/2504.09246)).

## Odin

**Status:** no 1.0. Monthly rolling snapshots, latest `dev-2026-07a` (2026-07-10). zlib licence ([FAQ](https://odin-lang.org/docs/faq/)). The project's own maturity framing: *"Odin as a language is pretty much done, but Odin the compiler, toolchain, and core library are still in development"*, with self-hosting explicitly deferred *"until after version 1.0"*.

**The wedge.** "The Data-Oriented Language for Sane Software Development", with four stated principles — Simplicity ("Simplicity is complicated to get right, clear is better than clever"), High Performance, Built for Modern Systems, and **Joy of Programming** ([odin-lang.org](https://odin-lang.org/)). gingerBill's own marketing post frames Odin as *"very pragmatic in terms of its design and overall philosophy"*, an *"alternative to C on modern systems"* that, rather than having one big idea, *"tries to solve the problems that other systems languages have failed to address"*, under the mantra *"There are no solutions, only trade-offs"* ([gingerbill.org](https://www.gingerbill.org/article/2024/09/08/odin-weird-to-market/)). Note that this post contains no direct comparison to Rust or Zig — Odin's "anti-Rust" positioning is mostly community framing, not the author's text. What it knowingly trades away is memory safety: gingerBill states Odin is not memory-safe but is *"safer than C by default"* via bounds checking and allocator discipline ([HN 43939520](https://news.ycombinator.com/item?id=43939520)).

**What it already solved** (from the [official Overview](https://odin-lang.org/docs/overview/) and [FAQ](https://odin-lang.org/docs/faq/)) — this list matters most, because re-implementing it is not differentiation:

- **Implicit `context`** carrying `allocator`, `temp_allocator`, `logger`, `assertion_failure_proc`, threaded through every call and swappable per scope. The signature feature.
- **Custom allocators** as the default idiom; arena/temp-allocator discipline instead of a GC or a borrow checker.
- **`defer`** at scope granularity.
- **Multiple return values + named results**, with `or_return`, `or_else`, `or_continue`. The FAQ's stated rationale: *"It is clear which procedure the error value is from compared to a try-catch approach"*.
- **`distinct` types** — nominal typing on demand.
- **Array programming and swizzling**: *"Builtin implicit swizzle fields are available on any array with length <= 4 as xyzw and rgba"*.
- **`#soa`** struct-of-arrays (incl. `#soa` slices and dynamic arrays), **`bit_set`**, built-in **`matrix`** with component-wise ops, **`quaternion`**.
- **Tagged unions** ("discriminated union… also known as a tagged union or sum type") with `switch in`, plus `Maybe(T)`.
- **Parametric polymorphism** (`$T` on procedures and structs), procedure groups for overloading, `using` for subtype polymorphism. The frequent claim that "Odin has no generics" is **false** — the FAQ lists "Parametric polymorphism ('generics')".
- **Package = directory**, DAG-only imports, integrated toolchain (`odin build .`, no external build system), and **vendored bindings shipped in-tree** (raylib, SDL, Vulkan).

Two corrections to common belief: Odin has `nil` as the zero value for pointers, slices and unions — **pointers are nullable**, and the safety story is optional-ok returns and union tags, not non-nullable-by-default. And Odin is **not** fast to compile; see below.

**What game devs praise.** The strongest primary source is Dale Weiler's review after ~50,000 lines of professional Odin at **JangaFX**, written with a disclosed conflict of interest ([graphitemaster.github.io/odin_review](https://graphitemaster.github.io/odin_review/)). He praises slices, built-in dynamic arrays and maps, `bit_set`, SOA, multiple returns, native `f16`, array programming, native matrices, discriminated unions, `defer`, `or_return`/`or_else`, trivial C FFI, the integrated toolchain and the vendored libraries. Production use is real: **EmberGen, LiquiGen and GeoGen are "written fully in Odin"**, and EmberGen is used by Bethesda, CAPCOM, Codemasters, THQ Nordic, Warner Bros and Weta Digital ([odin-lang.org](https://odin-lang.org/), [showcase](https://odin-lang.org/showcase/embergen/)). Shipped games from the official showcase: **CAT & ONION** (2024-02-01) and **Solar Storm** (2024-03-05) ([showcase](https://odin-lang.org/showcase/)). Named developers on HN report positively at scale: *"After several thousand lines, it proved all of my major worries incorrect"*; at 15k LOC it *"feels much higher level than it is"* ([HN 43939520](https://news.ycombinator.com/item?id=43939520)).

*Skepticism flag:* the widely-repeated JangaFX testimonials about "huge productivity" and "reduced bug density" trace to AI-generated content-farm articles, not to JangaFX. The official showcase page carries **no developer testimonial**. Treat the "why we switched" narrative as unsourced.

**What game devs complain about.** Almost all of it is toolchain, not language — and it comes from a friendly witness, which makes it more damning ([Weiler](https://graphitemaster.github.io/odin_review/)):

- **Debugging is broken:** *"The debugging experience for me personally has become so severely bad that none of the tools above work anymore, not even gdb."* DWARF3 generation crashes tools and causes miscompilation.
- **Compile speed:** *"The current Odin compiler is quite slow at compilation"*, with no caching or precompilation.
- **Codegen:** *"The compiler is not as aggressive at optimization as C or C++"* — no strict aliasing, no GVN, no devirtualisation; calling-convention overhead; *"No way to inline generics"*.
- **Procedure groups:** *"Procedure group resolution system needs to be completely rewritten."*
- Package system forbids sub-directory organisation; no import cycles; hidden allocations in literals.
- From HN: no official package manager (git submodules as the workaround); no compile-time conditional imports; setting up `context` inside cdecl C callbacks *"feels bad"*; the context system is *"rigid though convenient"*.

Complaints about docs and LSP maturity are commonly asserted but I found no strong primary evidence — `ols` is officially showcased and does not draw fire in the HN thread. Do not overstate that one.

**Simplicity mechanics.** Pascal/Go-flavoured: `name := value`, `name: Type = value`, `proc(a: int) -> int`. No semicolons, no headers, uniform declaration syntax — genuinely legible. But the concept count is far above Lua: allocators + context, arrays vs slices vs dynamic arrays vs `#soa`, `distinct`, `$T` parapoly, procedure groups, `or_return`, bit_sets, unions. Weiler names the real stumbling block as *"hidden reference/dereference semantics and slice behavior"*. For a Lua user the cliff is manual memory management, not syntax.

**Agent-friendliness.** 7,191 GitHub repos — ~0.6% of Rust's corpus, ~20% of Zig's. Beyond corpus size I found **no benchmark, no blog post and no GitHub issue** documenting LLM performance on Odin; the one article asserting it is AI-generated and worthless as evidence. *The following is labelled speculation:* the monthly `dev-YYYY-MM` rolling-release model plus a documented core-library migration ([Moving Towards a New core:os](https://odin-lang.org/news/), 2025-10-31) means older corpus encodes stdlib names that no longer exist — a structural poisoning risk. Odin's syntactic proximity to Go and Zig is a plausible cross-contamination hazard, uncited.

## Jai

**Status: still a closed beta after 6.5 years, compiler proprietary.** *"The compiler is currently proprietary, and the compiler should not be distributed to anyone outside of beta testers"*; on release *"it will have a permissive software license"*. Beta opened 2019-12-21; as of December 2025, v0.2.024 with roughly 800 enrolled testers ([The Way to Jai](https://github.com/Ivo-Balbaert/The_Way_to_Jai/blob/main/book/01B_What_is_Jai_-_more_in_depth.md)). Wikipedia's last verified statement is only *"As of August 2023, the Jai compiler is in a beta release"* ([Wikipedia](https://en.wikipedia.org/wiki/Jai_(programming_language))). **Evidence warning: nearly everything public about Jai is community reconstruction quoting a changelog most people cannot read. Treat all specifics below as second-hand.**

**The wedge.** *"The language is designed for good programmers; it has no training wheels for beginners"* (community paraphrase of Blow). Blow's own recorded position: C++ *"is a powerful language in some ways … but it makes [software development] a lot harder than it should be"*; the goal is to *"improve the experience of game programming"* and *"allow programmers to build more functionality with less code"* ([Wikipedia](https://en.wikipedia.org/wiki/Jai_(programming_language))). On safety, Blow *"considered modern 'memory safe' techniques too rigid for games."* The philosophy per the community wiki is to *"provide a series of broad tools to do whatever you want rather than enforce an object oriented hierarchy"* ([Jai Community Library](https://github.com/Jai-Community/Jai-Community-Library/wiki/Overview)). The trade is total: iteration speed and programmer power over safety, accessibility and availability.

**What it already solved** (per the [community wiki](https://github.com/Jai-Community/Jai-Community-Library/wiki/Overview)):

- **`#run`** — arbitrary compile-time execution of ordinary Jai code.
- **Full metaprogramming** — AST access via a compiler message loop; **hygienic macros**, not textual substitution; `#modify` for compile-time inspection and mutation of polymorphic instantiation.
- **The build system is a Jai program** — *"make-files or any other external build-systems are not needed"*, identically on every platform.
- **Implicit `context`** with swappable allocators — genuinely convergent with Odin.
- **`using`** for namespace injection and struct composition (Odin borrowed this).
- **SOA** as a first-class data-layout facility; data-oriented defaults.
- Parameterised structs, polymorphic procedures, multiple returns, operator overloading, block-scoped `defer`, no headers, no preprocessor, out-of-order compilation.
- **Explicitly rejected:** RAII, exceptions, constructors/destructors, GC. Debug-mode array/cast/math/null checks plus stack traces are the safety net.

**Compile speed** is the headline claim and it is unverifiable from outside: *"250,000 lines of code per second using the x64 backend, according to the CHANGELOG of beta 0.0.045"*, benchmarked on Thekla's own codebase, with a stated target of 1M LOC/sec ([The Way to Jai](https://github.com/Ivo-Balbaert/The_Way_to_Jai/blob/main/book/01B_What_is_Jai_-_more_in_depth.md)). Cite it as a vendor claim.

**What game devs praise / complain about.** There are essentially no shipped-game postmortems because there are essentially no shipped games. **Correcting a common assumption: *Braid, Anniversary Edition* was not written in Jai — it was C++**, like *The Witness* ([Wikipedia](https://en.wikipedia.org/wiki/Jai_(programming_language))). The only substantial Jai program is Thekla's engine for *Order of the Sinking Star* (~250k LOC), announced for 2026 and **not yet shipped**, so there is no postmortem at all ([Engadget](https://www.engadget.com/gaming/ten-years-after-the-witness-jonathan-blows-next-massive-puzzle-game-is-almost-ready-for-primetime-015727378.html); Thekla have said they will open-source *the engine* after release, which is not the same as the compiler). The complaints are structural facts rather than opinions: 6.5 years closed, ~800 testers, proprietary compiler, no public corpus, no package ecosystem, bus factor of one. Tooling is community-built and thin — a third-party LSP ([Jails](https://github.com/SogoCZE/Jails)) and editor plugins; the community library has 458 stars. A named practitioner's account exists in the ["Porting 58,000 lines of D and C++ to Jai"](https://lobste.rs/s/lsspr7/porting_58000_lines_d_c_jai_part_0_why_how) diary.

**Simplicity mechanics.** C-family with Go-ish declarations (`x := 5`, `f :: (a: int) -> int {}`). Superficially small, but the metaprogramming layer is a second language stacked on the first. A Lua user faces manual memory management *and* a compile-time metasystem with no analogue in anything they know.

**Agent-friendliness.** The worst case in this survey. 562 GitHub repos (unreliable, likely contaminated). The corpus is not merely small — idiomatic modern Jai sits behind a closed beta, so what leaks into crawls is six years of stale pre-1.0 syntax. No benchmarks, no reported failure modes, nothing. Any model writing Jai today is guessing.

## Zig

**Status:** 0.16.0 (2026-04-13); master is 0.17.0-dev ([downloads](https://ziglang.org/download/)). MIT. Zig Software Foundation, a 501(c)(3). Eleven years in, **no 1.0**.

**The wedge.** "No hidden control flow, no hidden allocations, no preprocessor, no macros" ([ziglang.org](https://ziglang.org/)). `comptime` replaces both generics and macros; C interop and cross-compilation are first-class, and `zig cc` ships a full clang-based C/C++ toolchain. Traded away: RAII/destructors, operator overloading, exceptions, and — since 0.15 — language-level async. The wedge got *sharper* in a way worth studying: 0.16.0 makes I/O an explicit parameter, introducing `std.Io` threaded through every call site (`std.fs` → `std.Io.Dir`/`std.Io.File`, `std.net` → `std.Io.net`, `std.Thread.Mutex` → `std.Io.Mutex`) ([0.16.0 release notes](https://ziglang.org/download/0.16.0/release-notes.html)), the "no function colouring" answer to async ([Loris Cro](https://kristoff.it/blog/zig-new-async-io/)).

**Robustness mechanics.** Error unions with explicit error sets, `try`, `defer`/`errdefer`, optionals `?T` with no null, allocators passed as parameters, tagged unions with exhaustive `switch`, safety-checked release modes (ReleaseSafe), `build.zig`.

**What game devs praise — thin, and worth saying bluntly.** I could not source a single shipped commercial game in Zig. The community's own state-of-the-ecosystem page says Zig is used "by both hobbyists for side projects, as well as a few seriously committed individuals who do Zig game development full time", that "general purpose engines/frameworks/ecosystems are in early stages of development", and the only named game it lists is a Pac-Man clone ([allyourcodebase.com/gamedev](https://allyourcodebase.com/gamedev/)). Mach is pre-1.0 with no production-readiness claim ([machengine.org](https://machengine.org/), [devlog](https://devlog.hexops.org/2024/mach-v0.3-released/)). The strongest evidence is `foxnne`'s Pixi and Aftersun — tools and WIP ([github.com/foxnne/aftersun](https://github.com/foxnne/aftersun)). The load-bearing praise is non-game: TigerBeetle, Bun, and `zig cc` used as a cross-compiling toolchain by projects that write no Zig at all. "Zig is great for gamedev" is aspiration backed by tooling quality, not by shipped product.

**What game devs complain about — churn, and it is fully documented.** From the official release notes:

- **0.15.1, "Writergate":** "All existing `std.io` readers and writers are deprecated in favor of the newly provided `std.Io.Reader` and `std.Io.Writer` which are *non-generic*." ([0.15.1 notes](https://ziglang.org/download/0.15.1/release-notes.html))
- **0.15.1:** `usingnamespace` removed entirely.
- **0.15.1:** `async`/`await` keywords and `@frameSize` removed — "There will not be async/await keywords in the language."
- **0.15.1:** `std.ArrayList` now means the unmanaged variant; managed moved to `std.array_list.Managed`.
- **0.16.0**, eight months later: the entire I/O surface moved again; `@Type` split into `@Int`/`@Struct`/`@Union`/`@Fn`/`@Enum`; `ThreadSafeAllocator`, `SegmentedList`, `std.once` and `std.Thread.Pool` removed.

Two consecutive releases each rewrote the most-used part of the standard library. Add package-manager churn ([devlog](https://ziglang.org/devlog/2026/)) and a twelve-month-old codebase does not compile.

**Simplicity mechanics.** Small keyword count, high conceptual load. Explicit allocators put plumbing in every non-trivial signature that a Lua user has never seen; 0.16 added a second threaded parameter for I/O. `comptime` is one mechanism doing three jobs — elegant in the small, opaque in the large. The documented bite is `anytype`: it "suffers in readability because there is no separation between comptime type validation logic and runtime logic", you must "compile, fail, and see in error messages" what a type is, and it "feels like programming in a dynamically typed language" ([Renato Athaydes](https://renato.athaydes.com/posts/comptime-programming); open proposals [ziglang/zig#17198](https://github.com/ziglang/zig/issues/17198), [#9107](https://github.com/ziglang/zig/issues/9107) — Zig core acknowledges the problem). See also [ForrestTheWoods, "Failing to Learn Zig via Advent of Code"](https://www.forrestthewoods.com/blog/failing-to-learn-zig-via-advent-of-code/).

**Agent-friendliness — the strongest documented finding in this survey, and it is negative.** Named developers on Ziggit ([ziggit.dev/t/zig-and-ai-coding/12840](https://ziggit.dev/t/zig-and-ai-coding/12840)): LLMs generate from "outdated syntax learned from countless legacy examples"; a model claimed "typecheck went fine so there are no bugs" then looped "introducing new mistakes and fixing those… only to end up with exactly the same code"; "LLMs have a tendency to output very subtle mistakes that only show up far into the future". The failure modes map one-to-one onto the churn list: `root_source_file` instead of `root_module`, pre-Writergate I/O, `ArrayList` without a threaded allocator, emitting removed `async`/`usingnamespace`. Mitigation projects exist *because* the problem is real ([zig-skills](https://github.com/nzrsky/zig-skills), built to stop LLMs "generating code with deprecated or removed APIs"); there is a public bake-off ([Comparing the Top LLMs on the Zig Challenge](https://akitaonrails.com/en/2026/01/11/ai-agents-comparing-top-llms-on-the-zig-challenge/)) and an HN thread titled "Have you ever used an LLM with Zig? It will generate syntactically invalid code" ([HN 46862586](https://news.ycombinator.com/item?id=46862586)).

The project is also **hostile to LLMs by policy**: the Code of Conduct bans "No LLM-generated content, whether it be code or prose. No paraphrasing LLM-generated content. No LLMs for editing… No LLMs for translation", plus LLM brainstorming and bug-finding ([ziglang.org/code-of-conduct](https://ziglang.org/code-of-conduct/)). Kelley reportedly called such contributions "invariably garbage" with "negative value" (May 2026) — *sourced via secondary reporting rather than a transcript; treat wording as approximate*. Zig placed 4th most-admired language at ~64% in the [2025 Stack Overflow survey](https://survey.stackoverflow.co/2025/technology); admiration does not produce training tokens.

## Beef

**Status:** last tagged release 0.43.5 (2025-03-19), but commits land daily. One maintainer, Brian Fiete — PopCap co-founder and former CTO, working "more or less full-time on BeefLang since September 2014", first public release January 2020 ([FAQ](https://www.beeflang.org/docs/faq/)). 2,821 stars.

**The wedge.** "A high-performance multi-paradigm open source programming language with a focus on developer productivity" ([beeflang.org](https://www.beeflang.org/)). The distinguishing bet is **tooling-first**: a bundled IDE with debugger and profiler, hot compilation (edit-and-continue on a running game), real-time leak detection, and deliberately good *debug-build* performance — the thing C++ gamedevs actually suffer from. C#-shaped syntax over manual memory management. The gamedev intent is explicit: "The majority of game development is performed on Windows, and it's critical to concentrate on making that primary development platform experience as good as possible."

**Mechanics.** Compile-time function evaluation and code generation, custom allocators, batched/append allocations, pattern matching, tagged unions, tuples, generics, interfaces, `defer`, nullable refs, reflection, runtime bounds and leak checks in debug builds ([language guide](https://www.beeflang.org/docs/language-guide/)). The homepage advertises Tier-3 Switch/PS5/Xbox support, but **the FAQ says console development "has not yet started"** — trust the FAQ.

**What shipped: essentially nothing public.** I found no commercially shipped game written in Beef. Six years after public release, from the co-founder of the studio that made *Plants vs. Zombies*. There are engine bindings, a "Space Game" sample, and itch.io hobby projects. **This is the most instructive fact in the survey**: a gamedev-native language with a decade of full-time work, hot reload and a bundled debugger — precisely the feature set gamedevs say they want — with no shipped titles. Feature-correctness does not produce adoption.

**Complaints.** The bus factor is quantifiable: `bfiete` has 5,066 commits; the next contributor 149. Release cadence is effectively dead — one tagged release in the 30 months between Sep 2022 and Mar 2025 — so in practice you run unversioned nightlies. 252 open issues. Windows-centric by design. IDE lock-in is the flip side of the IDE being the selling point.

**Simplicity mechanics.** Syntactically the friendliest of the C-replacement group — C# is a mainstream, well-taught shape, and an integrated debugger lowers the on-ramp more than any language feature. But it is a large language (generics + interfaces + reflection + comptime + operator overloading + pattern matching): concept count closer to C# than to Lua.

**Agent-friendliness.** Corpus negligible (395 repos), no survey presence, no benchmark exists because nobody has bothered. *Speculation, flagged:* C#-shaped syntax means models will produce plausible-looking Beef by pattern-transfer from C#, which is arguably a worse failure mode than Zig's — Zig fails loudly at compile time, whereas Beef would fail by silently importing C# idioms (GC assumptions, `using`, LINQ) that do not exist. No evidence either way.

## C3

**Status:** v0.8.2 (2026-07-10), MIT, one maintainer (Christoffer Lernö). 5,691 stars. The 0.8.0 post is titled "The Core Language Is Settling" ([c3-lang.org/blog](https://c3-lang.org/blog/)) — settling, not settled.

**The wedge.** "C3 is an evolution, not a revolution: the C-like for programmers who like C" ([c3-lang.org](https://c3-lang.org/)). Full C ABI compatibility is load-bearing: you keep the entire C ecosystem. Advertised: module system, semantic macros, compile-time and runtime reflection, gradual contracts, inline assembly as normal code, "zero-overhead error handling combining Results with exception-like usability", extensive debug-mode checks, generic modules, debug stack traces.

**Mechanics — and a cautionary tale for a Lua-simple goal.** Optionals/faults are the interesting design, but the syntax is dense ([optionals-advanced](https://c3-lang.org/language-common/optionals-advanced/)): `int? x = f();` for an Optional holding a result or an "Excuse"; `File file = file::open(name, "r")!;` where `!` rethrows; `int v = f() ?? -1;`; `f()!!` to panic; plus `if (catch excuse = x)`, `if (try x)`, `@catch()` and `@ok()`. That is five-plus operators and forms for a single concept. Contracts (`@require`/`@ensure`) are advertised on the front page but their documentation depth was not verified.

**What shipped.** Nothing commercial that I could source. There are raylib bindings ([raylib.c3l](https://github.com/NexushasTaken/raylib.c3l)) with native and browser targets and a Tsoding demo ([tsoding/c3-demo](https://github.com/tsoding/c3-demo)). Hobby-scale.

**Complaints.** Same ~90% bus factor as Beef (`lerno` 3,779 commits; next contributor 94). Core semantics are still churning in 2026: ["Unsigned sizes: a five year mistake"](https://c3-lang.org/blog/) (2026-05-02) reverses a 2021 decision, with Lernö writing "I'm a bit embarrassed about how long it took for me to change this"; a week later, "Let's kill off half the builtins in 0.8.0". Credit for the candour, but a language reversing its size-type signedness at v0.8 is not stable. The real problem is differentiation: against C you gain safety and lose ubiquity; against Zig you gain C familiarity and lose comptime and a funded foundation; against Odin you lose the gamedev-native stdlib.

**Simplicity mechanics.** Best-in-class for an existing C programmer; **worst-in-class for a Lua user**. You inherit C's declaration syntax, pointer semantics and manual memory, then add modules, `@` macros, generic modules, contracts and the optional/fault operator zoo. Concept count strictly greater than C's.

**Agent-friendliness.** Effectively zero corpus (327 repos, unreliable). *Speculation, flagged:* the specific trap is that because C3 *looks* like C, models will emit C and call it C3 — faults, `!`/`??`/`!!`, module syntax and generic modules have no C analogue, so the near-miss rate should be high and the errors semantic rather than syntactic. Same mechanism documented for Zig, amplified by surface similarity to a huge corpus. No benchmark exists.

## Nim

**The wedge.** Expressive power per line plus compile-time metaprogramming, traded against ecosystem size and toolchain stability. Araq's [*Zen of Nim*](https://nim-lang.org/blog/2021/11/15/zen-of-nim.html) is the best statement of intent: "Copying bad design is not good design"; "Programs are read way more often than they are written"; "Programs are run more often than they are compiled" (the justification for compile-time evaluation); "If the compiler cannot reason about the code, neither can the programmer"; and on features, "instead of building these features into the language, let's have a macro system" covering locking, logging, lazy evaluation, DSLs and parallelism. He also concedes the drift: "The older Nim gets the more Nim is about completeness (all minimal languages grow to serve certain needs)."

**Memory management, verified and qualified.** ORC has been the default since Nim 2.0. Both ARC and ORC "offer deterministic performance for hard realtime systems", and "Since algorithms based on 'tracing' are not used, the runtime behavior is oblivious to the involved heap and stack sizes" ([mm docs](https://nim-lang.org/docs/mm.html)). **But the "no GC pauses" claim needs a qualifier that Nim's own blog supplies:** ORC "retains most of ARC's advantages *except determinism (partially)*", because the cycle collector runs on an adaptive threshold, and it "produces more machine code than `--mm:arc`" ([Introduction to ARC/ORC](https://nim-lang.org/blog/2020/10/15/introduction-to-arc-orc-in-nim.html)). There is also a trap for async game code: "the default async implementation produces cycles and leaks memory with `--mm:arc`", so you cannot simply select the deterministic mode. Six `--mm:` modes exist in total.

**Robustness features and their sharp edges.** Nim 2.0 made ORC default, added `strictDefs` (must-initialise-before-use with control-flow analysis), and tightened the effect system — "strict effects require callback parameters to be annotated with `effectsOf`", plus a mechanism to forbid specific effects while ignoring others, aimed at preventing accidental cross-layer calls ([2.0 RC post](https://nim-lang.org/blog/2022/12/21/version-20-rc.html)). That last one is directly interesting for a game engine with hard layer boundaries (no allocation in the render loop).

`not nil` / `--experimental:strictNotNil` is the weak link, and the manual says so itself ([manual_experimental](https://nim-lang.org/docs/manual_experimental.html)): the analysis is "currently control flow insensitive" and produces false positives; it "should take exceptions into account (but currently does not)"; array element tracking supports "only constant indices"; and the documented workaround is to switch the warning off locally. **If ludo wants nil-safety, Nim is a cautionary tale, not a model — retrofitting it as an opt-in analysis produces a feature nobody can rely on.** Nim 2.0 also shipped real breakage: `gc:v2` removed, `TaintedString` gone, nil-to-distinct-pointer assignment needing explicit conversion, and much of `system` split into `std/syncio`, `std/assertions`.

**What game devs say — honest answer: it is hobby-scale.** [Nico](https://github.com/ftsf/nico) is a PICO-8-inspired SDL2 framework with a jam-game collection on [itch.io](https://itch.io/c/1064082/games-made-with-nico); [Naylib](https://github.com/planetis-m/naylib) gives idiomatic raylib bindings; Godot bindings exist. I found **no commercially shipped Steam title in Nim**. Nim's real production flagship is Status's Nimbus Ethereum client, which tells you the gamedev story is aspirational.

**Complaints.** Ecosystem size is the most consistent theme across HN threads ([44931578](https://news.ycombinator.com/item?id=44931578), [39861687](https://news.ycombinator.com/item?id=39861687)) — repeatedly "the language is good, the ecosystem is another story" (anecdotal, but consistent). [nim-lang/Nim](https://github.com/nim-lang/Nim) carries 2,179 open issues against 18.1k stars. A 2025 forum post, ["The turbulent evolution of Nim's concurrency story"](https://forum.nim-lang.org/t/13322), reportedly documents threadpool deprecation, async leaks under ORC, a ~40% threading regression in 2.0 and an `asyncdispatch` vs `chronos` split — **the thread body could not be loaded; treat those specifics as unverified**, though the async-leak part is corroborated by the mm docs. On governance: the hard fork [nim-works/nimskull](https://github.com/nim-works/nimskull) exists and self-describes as "We, the community of users, maintain it"; the [HN thread](https://news.ycombinator.com/item?id=32021299) carries the usual leadership accusations. **Report the fork as fact and the reasons as disputed** — no primary response from Araq was found. Generic/macro error messages draw recurring complaints ([RFC #323](https://github.com/nim-lang/RFCs/issues/323)) but no rigorous study exists.

**Simplicity mechanics.** Indentation-based and genuinely Python-adjacent to read, but Nim is not a small language: macros, templates, `distinct`, object variants, concepts, effect tracking, five-plus `--mm:` modes and multiple `--experimental:` switches. A beginner can *read* it and cannot *predict* it — the opposite of what "Lua-simple" has to mean.

**Agent-friendliness.** 13,403 repos. **No published evaluation exists.** Structurally, the corpus is split across pre- and post-2.0 idioms (`--gc:` vs `--mm:`, the `system` reorganisation), so model output should mix incompatible eras. Flagged as evidence-free prediction.

## Luau

**The wedge.** Luau optimises for *not annoying a heterogeneous user base*, at explicit cost to type-system rigour. Official goals: "making the language more performant and feature-rich, and make it easier to write robust code through a combination of linting and type checking using a gradual type system" ([luau.org/why](https://luau.org/why)). The binding constraint is backward compatibility — "we also could not afford to do major breaking changes to the language" — which is why Luau is still a Lua **5.1** derivative in 2026.

The clearest statement of the trade is in the Roblox team's own HATRA'21 paper ([Brown, Friesen, Jeffrey](https://asaj.org/papers/hatra21.pdf)). Two modes with *opposite* correctness targets: non-strict mode, for non-professionals, is "focused on minimizing false positives (that is, in non-strict mode, any program with a type error has a defect)"; strict mode, for professionals, is "focused on minimizing false negatives (that is, in strict mode, any program with a defect has a type error)". Neither is soundness. The paper is candid about the user model — onboarding is "Google the task, then cut-and-paste the resulting code, adapting it as needed", therefore "for most goal-driven developers, the type system should help or get out of the way." Types exist primarily to power autocomplete and API docs.

**Where the hole is, precisely — the most useful finding in this survey.** HATRA'23 ([same authors](https://asaj.org/papers/hatra23.pdf)) records that Luau deliberately *rejected* Siek–Taha gradual typing:

> "Rather than the gradual typing approach of Siek and Taha, which uses consistent subtyping where `any ~ τ` for any type τ, we adopt an approach based on **error suppression**, where `any` is an **error-suppressing type**, and any failures of subtyping involving error-suppressing types are not reported."

And the soundness theorem they can actually prove is conditional:

> "To retain type soundness (**in the absence of user-supplied error-suppressing types**) we show that … the usual 'well typed programs don't go wrong' type soundness result **for programs without explicit error-suppressing types**."

Luau is sound only over the `any`-free fragment. One `: any`, and errors are suppressed *transitively* — an expression with a type error itself acquires an error-suppressing type, by design, to avoid cascades. This is a cleaner formulation of the hole than TypeScript's, because it is honest about being an error-*reporting* policy rather than a typing relation. The user-facing docs are much less candid: [luau.org/types](https://luau.org/types) documents `--!nocheck` / `--!nonstrict` (default; "if we can't figure out what type something is early on, we infer the type could be anything (the `any` type) and let you proceed without errors") / `--!strict`, and makes no soundness admission at all.

**Inference limits, in their own words.** HATRA'23's Further Work section: "Currently the type inference system uses **greedy inference**, which is very sensitive to order of declarations, and can easily result in false positives." And: "Currently, non-strict mode … inferring `any` as the type for local variables … **does not play well with type-directed tooling, for example `any` cannot provide autocomplete suggestions**." That is self-inflicted — the mode designed to be friendly to beginners destroys the tooling that justified having types.

The other inference cliff is **table sealing**: a table literal starts unsealed (properties can be tacked on) and becomes sealed when annotated, returned from a function, or when its scope exits, after which adding a field is an error ([tables](https://luau.org/typecheck/tables), [RFC](https://rfcs.luau.org/unsealed-table-literals.html)). It is the commonest "why does this work here but not there" confusion, and it exists purely so Lua's `t.x = 1` idiom keeps working.

**The hardest number: opt-in typing does not get adopted.** Greenman, Jeffrey, Krishnamurthi & Shah, *Privacy-Respecting Type Error Telemetry at Scale* ([arXiv:2403.02409](https://arxiv.org/pdf/2403.02409)), 1.5M telemetry records from 340,000 Roblox Studio sessions:

> "One of the **less-surprising** findings is that **opt-in gradual types are unpopular: there is a 100x gap between the number of untyped Luau sessions and the number of typed ones**."

> "One surprise is that the strict mode for type analysis is **overly conservative about interactions with data assets**."

`SyntaxError`, `UnknownSymbol` and `UnknownProperty` dominate the error mix, and the authors conclude "most errors in the data are likely due to typos during edits" — the checker mostly functions as a spell-checker. Next commonest are `CountMismatch` (arity), `TypeMismatch`, `GenericError`. Roblox has since acted: non-strict, not `nocheck`, is now the default.

**New solver status (2026).** General release announced 2025-11-20; the Studio beta flag was removed 2026-01-07; the old solver stays supported through 2026 for migration ([announcement](https://devforum.roblox.com/t/general-release-luaus-new-type-solver/4084991)). Rollout is asymmetric — `nocheck`/`nonstrict` users got it automatically, while existing **strict-mode** projects stay on the old solver unless they opt in via `UseNewLuauTypeSolver`. New: read-only table properties, better refinements and singleton handling, type functions, relaxed casting. Roblox's own admitted known issues: types and error messages that are "larger and more verbose, or otherwise less clear than the old system"; performance "slower than desired" with "excessive memory usage in Roblox Studio"; remaining correctness bugs with strict mode "too strict". Developer replies complain of false-positive walls, messages "needlessly complicated and vague compared to other engines like Unity", and open-source modules that no longer type-check — **a real ecosystem-split cost from a solver change alone, with no syntax change involved.**

**Praise and real usage.** Scale is the justification: "approximately 20 million experiences … created by 8 million developers" as of 2021, "hundreds of millions of users, and millions of creators" by 2023 (HATRA papers). Non-Roblox adoption is real but thin, and the detail matters: Remedy's Northlight engine uses Luau in *Alan Wake 2*, replacing a proprietary scripting language and eliminating "80 000 lines of code we no longer need to maintain" ([remedygames.com](https://www.remedygames.com/article/how-northlight-makes-alan-wake-2-shine); corroborated by Remedy engineer Petri Häkkinen's [own post](https://x.com/petrih3/status/1721977448491815178)) — **but Remedy's article says nothing about the type checker; the win they describe is embeddability and live editing.** Lune, the standalone runtime, is small (~920 stars vs Luau's ~5.7k).

Two things worth stealing outright. **Sandboxing:** `io`, `package`, `dofile`/`loadfile`, `string.dump`, `load` and most of `debug` are removed; `os` is trimmed to `clock`/`date`/`difftime`/`time`; globals and the string metatable are readonly; each script gets a per-script global table via `__index`; there is a VM-level interrupt for runaway scripts; no `__gc` ([luau.org/sandbox](https://luau.org/sandbox)) — they claim no known escapes while conceding no formal proof exists. **Native codegen** takes "into account the type annotations present in the source code to specialize code paths" but with "no runtime analysis of the types/values flowing through the program" ([performance](https://luau.org/performance)) — and note the honest limit: type info is currently used only for "small peephole optimizations". Annotations buy far less speed than people assume.

**Simplicity mechanics.** Un-annotated Luau *is* Lua 5.1; a Lua user recognises it instantly. That is the whole compatibility bet. The perceived-complexity cost appears only at the seams — sealed/unsealed tables, `::` casts, the mode pragma. Combined with the 100x telemetry gap, the picture is that the typed layer is cheap to ignore and therefore mostly ignored.

**Agent-friendliness.** Roblox's Code Assist reports "creators have adopted about **300 million characters** of code suggested by Code Assist" during beta, from an in-house model fine-tuned on "a small subset of free Creator Store items and the scripts creators share via our data sharing program" ([devforum](https://devforum.roblox.com/t/code-assist-full-release-ai-powered-code-completion/2848978)). Roblox admits it "still requires scripters to review and modify the code suggestions" and is "primarily designed to assist proficient Roblox scripters" — explicitly not beginners. **No accuracy or acceptance-rate numbers have been published; characters-adopted is a vanity metric.** The Lua/Luau conflation failure mode is documented only anecdotally: a community tool author reports ChatGPT and Gemini "struggle with Roblox specifics… getting back deprecated APIs, functions that don't exist, or scripts that try to write to ServerStorage from a LocalScript" ([devforum](https://devforum.roblox.com/t/beta-rocode-the-ai-coding-assistant-built-specifically-for-luau-roblox/4116633)). Anecdote, but exactly the failure mode predicted for any Lua dialect.

## Teal

**The wedge.** Compile to plain Lua, and let that constraint dictate the type system. Hisham Muhammad's pitch is documentation-plus-checking, not proof: "Coding with types is like pair programming with the machine", with the caveat "Of course, it cannot catch every possible mistake in a program, but it should help you with things like typos in table fields, missing arguments and so on" ([why_types.md](https://github.com/teal-language/tl/blob/master/docs/src/why_types.md)).

**Why unions are restricted — the answer is structural, not philosophical, and it is the sharpest finding here.** From [current_limitations_on_union_types.md](https://github.com/teal-language/tl/blob/master/docs/src/current_limitations_on_union_types.md): (1) "the `is` operator always matches a variable, not arbitrary expressions. This limitation is there to **avoid aliasing**." (2) "Teal only accepts unions over a set of types that it can **discriminate at runtime**, so that it can **generate code for the `is` operator properly**." So `{string} | {number}`, `{string} | {string:string}` and `{string} | MyRecord` are all rejected, because `is` lowers to Lua's `type()`, which returns `"table"` for all of them. Multiple table types in a union need records/interfaces carrying `where` discriminator clauses. Enums are likewise blocked because enums are strings at runtime. And the escape hatch is explicitly unverified: "Teal has **no way of proving at compile time** that the set of `where` clauses in the union is actually disjoint … **that is up to you**."

**Lesson for ludo:** if you compile to a host language and want runtime-checked refinements, the host's runtime type tags become a hard ceiling on your type algebra. A natively-compiled language pays no such tax and can afford real tagged sums. This is a genuine structural advantage over both Teal and Luau, and the single biggest thing Teal gives away.

**The `any` hole** is smaller and better-behaved than Luau's: "since Teal doesn't know anything about this value, there isn't much you can do with it, besides comparing for equality and against nil, and casting it into other values using the `as` operator", and it exists for ecosystem reasons — "Some Lua libraries use complex dynamic types that can't be easily represented in Teal. In those cases, using `any` and making explicit casts is our **last resort**" ([the_type_any.md](https://github.com/teal-language/tl/blob/master/docs/src/the_type_any.md)). Unlike Luau's, Teal's `any` does not silently suppress downstream errors; you must write `as` at each boundary. More honest, more annoying.

**Ecosystem split, quantified.** `.d.tl` declaration files annotate untyped Lua/C modules; the community repo [teal-language/teal-types](https://github.com/teal-language/teal-types) covers roughly **44 libraries** (argparse, busted, lpeg, luafilesystem, luasocket, penlight, inspect, neovim, luv, dkjson, bump, hump, flux, lume, …) and has 135 stars. LuaRocks hosts thousands of modules. **Typed coverage of the Lua ecosystem is on the order of one percent.** There is a second, subtler leak: tl "declares all entries of the standard library as `<const>`, and assumes that Lua libraries don't modify it. If your Lua environment modifies the standard library with incompatible behaviors, **tl will be oblivious to it and you're on your own**" ([compatibility doc](https://github.com/teal-language/tl/blob/master/docs/src/teal_standard_library_and_lua_compatibility.md)). Monkey-patching is idiomatic Lua; Teal declares it out of scope.

One game-adjacent affordance worth copying: `global_env_def` in `tlconfig.lua` declares a preloaded global environment, and the docs use LÖVE's `love` table as the example ([declaration_files.md](https://github.com/teal-language/tl/blob/master/docs/src/declaration_files.md)) — directly relevant if ludo needs to describe an engine-provided global namespace.

**Adoption — honest assessment.** [teal-language/tl](https://github.com/teal-language/tl): 2,786 stars, 129 open issues, created Feb 2019, actively maintained as of July 2026, single-maintainer-dominated (Hisham also created LuaRocks and htop, so the LuaRocks integration is not accidental). No large public production user surfaced in primary sources. Unlike Luau, Teal has no platform forcing function — nobody is required to use it. Hisham's three talks ("Minimalism versus types", 2019; "Minimalistic typed Lua is here", 2020; "What's Next for Teal", 2021) are listed at [hisham.hm/talks](https://hisham.hm/talks), but the decks are vector PDFs with no extractable text and were not quotable.

**Simplicity mechanics.** Teal reads as Lua with annotations plus `record`/`interface` blocks; a Lua user recognises ~90% of it. It is the closest thing in this survey to "what Lua-with-types feels like".

**Agent-friendliness.** Teal's worst axis: 43 repos, and **no published evaluation of LLM performance on Teal exists at all**. The predictable failure mode — a model emitting valid Lua that Teal rejects (untyped globals, unrestricted unions, monkey-patching) — is highly likely but unmeasured. Say "unmeasured", not "known".

## DragonRuby — the outlier

The assignment was to find out what DragonRuby *actually did* to earn a feel of joy rather than a claim of it. The answer is unusually verifiable, because the engine's ~100 Ruby runtime files are public and MIT-licensed ([dragonruby-game-toolkit-contrib](https://github.com/DragonRuby/dragonruby-game-toolkit-contrib)) even though the product is closed and paid.

**The wedge.** Optimise for shipping-a-game-today; trade away performance ceiling, static safety, and ecosystem. The philosophy doc says it outright ([philosophy.md](https://docs.dragonruby.org/misc/philosophy.md)): "Building A Game Should Be Fun And Bring Happiness — We will prioritize the removal of pain", and "Real artists ship."

**Runtime.** A fork of **mRuby** (not CRuby), SDL, and LLVM, in six layers per the vendor's FAQ, up to "a Ahead of Time/Just in Time Ruby compiler built with LLVM… but only supports a subset of the Ruby language specification" ([faq.md](https://docs.dragonruby.org/misc/faq.md)); that compiler is public as [DragonRuby/lightstorm](https://github.com/DragonRuby/lightstorm), the patched interpreter as [mruby-patched](https://github.com/DragonRuby/mruby-patched). Authorship is confirmed first-party — the Quick Start is written by **Ryan C. Gordon (icculus)**, who says *"I (Ryan Gordon) wrote the C parts of this toolkit and Ruby looks a little strange to me (Amir Rajan wrote the Ruby parts…)"* ([getting-started.md](https://docs.dragonruby.org/guides/getting-started.md)). Binary size is claimed under 10 MB on the vendor's itch devlog — **unverified; itch.io refuses automated fetch, so this is a search-snippet only.**

**Hot reload — the real mechanism, and the real number.** `hotload.rb` polls file mtimes *inside the game loop*, with a frame-rate-compensated debounce that fires at 60, i.e. **a scan about once per second at 60 fps**. Worst-case save-to-effect latency is therefore ~1 second plus parse time — there is no filesystem-notification path and no sub-frame reload. Two details matter far more than the latency: (1) `files_to_reload` includes ~100 *engine* files (`dragon/args.rb`, `dragon/outputs.rb`, even `hotload.rb` itself) alongside your `app/main.rb` — engine and game code are the same kind of thing; (2) **reload does not reset state.** `args.state` survives; only `DR.reset` clears it ([state.md](https://docs.dragonruby.org/api/state.md)). Change gravity mid-jump and the jump continues with the new gravity. There is also a `repl.rb` convention where code inside a `repl do … end` block **executes on file save**, with an `xrepl` prefix to comment it out ([faq.md](https://docs.dragonruby.org/misc/faq.md)).

**Errors pause the game; they do not kill it.** Verified in [`dragon/runtime.rb`](https://github.com/DragonRuby/dragonruby-game-toolkit-contrib/blob/master/dragon/runtime.rb): the whole tick is wrapped in `rescue Exception`, which records the tick, writes game state and the exception to `logs/exceptions/`, pretty-prints, shows the in-game console, **pre-fills the console prompt with a recovery command including the RNG seed** (`GTK.reset seed: <rng_seed>`, or `GTK.reboot` on a `superclass mismatch` error), and then calls **`pause!`**. `reload_if_needed` carries the comment *"in the event that an exception was thrown on initial load, if a file is changed, set load status to :dragonruby_started so that initialization can be tried again"*, and `unpause_if_needed` notes *"attempt to unpause the game if the console is closed (maybe an exception was fixed within the console)"*. **The failure mode is a pause, not a restart** — that, more than any single feature, is the mechanical basis of the "joy" feel. The vendor also concedes the limit and answers it with determinism: *"Debugging something that runs at 60fps is (imo) not that helpful. The exception you are seeing could have been because of a change that occurred many frames ago"* — hence `--record` / `--replay`.

**Ceremony removal.** Gordon's framing of the model: *"Your game is all going to happen under one function … that runs 60 times a second … That's an entire video game in one run-on sentence."* Rendering is data-as-API and immediate-mode: *"In DragonRuby, you use hashes to draw things and we figure out the details… You don't need to know about graphics APIs. You're just setting up some hashes! DragonRuby clears out `args.outputs` every frame"* — canonically `args.outputs.sprites << { x: 576, y: 100, w: 128, h: 101, path: 'dragonruby.png' }`. The screen is **always 1280×720**, letterboxed on resize, origin bottom-left, justified on gameplay-ergonomics grounds ("when you're making Super Mario Brothers and you want Mario to jump, you should be able to add to Mario's y position"). Removing resolution-independence as a problem is a deliberate cut. `args.state` is *"a property bag… useful for rapid prototyping, especially when you're not ready to commit to using classes"*; idiomatic init is `args.state.player ||= { x: 0, y: 0 }` inside `tick` — no schema, no constructor, no init phase. *(Correction to the common framing: the current docs are moving away from full auto-vivification, recommending `args.state = {}` in `boot` and warning that "future versions of DragonRuby will enforce `args.state` initialization during boot.")*

**The layering paragraph — the most directly relevant text in this entire survey.** From [philosophy.md](https://docs.dragonruby.org/misc/philosophy.md):

> "There is a programming idiom in software called 'The Pit of Success'. The term normalizes upfront pain as a necessity… This approach to development is strongly discouraged by us. It leads to over-architected and unnecessary code; creates barriers to rapid prototyping and shipping a game; and overwhelms beginners… DragonRuby's philosophy is to provide multiple options across the 'make it fast' vs 'make it right' spectrum, **with incremental/intuitive transitions between the options provided**. A concrete example… render primitives: tuples/arrays (easy to pickup, simple, and fast to code/prototype with), hashes (a little more work, but gives you the ability to add additional properties), open and strict entities (more work than hashes, but yields cleaner apis), and finally… classes."

That is a written spec for a layered language, shipped by a vendor. Note the axis: the layering is along **ceremony**, not along beginner/expert. And the ladder is real in the API — arrays → hashes → `new_entity` → `new_entity_strict` → classes with `attr_dr`, where `StrictEntity` exists specifically so a typo'd property raises instead of silently auto-vivifying, recommended as a correctness *and* performance upgrade ([readme_docs.rb](https://github.com/DragonRuby/dragonruby-game-toolkit-contrib/blob/master/dragon/readme_docs.rb)).

**Distribution.** Zero-install, zero dependency manager, and deliberately so: *"DragonRuby does not support gems because that requires the installation of MRI Ruby on the developer's machine (which is a non-starter given that we want DragonRuby to be a zero dependency runtime)."* Download a zip, edit `mygame/app/main.rb`, run `./dragonruby`. Pricing ([dragonruby.org](https://dragonruby.org/)): Standard **$48 one-time**; Indie **$96/yr** (C extensions, bytecode compilation); Pro **$128/yr** (mobile, HD/4K, VR preview), with free Standard licences for under-18s, students, teachers, public servants and anyone earning under $2000/month. Closed source on purpose: *"The current state of open source is unsustainable… Parts of DragonRuby are in fact, open source. Just not all of it."* Platform claims include Switch/PS4/Xbox, but **consoles are NDA-gated bespoke arrangements, not a purchasable tier** — public evidence of shipped console titles is secondary. **Correction worth carrying forward: Amir Rajan's *A Dark Room* iOS success was built with RubyMotion, not DragonRuby GTK** ([RubyMotion success story](http://www.rubymotion.com/references/success-stories/a-dark-room/)); conflating the two overstates DragonRuby's shipping record.

**What devs complain about.** The best independent writeup ([silverhammermba, 2022](https://silverhammermba.github.io/blog/2022/02/19/dragonruby)) praises the loop — *"Whenever you save a source file, DragonRuby picks up the differences and almost instantly incorporates them"* — and the console *"not restricted to some specific subset of functionality, it uses the very language that the rest of your game is written in."* Its complaints are the useful part: *"It provides too many ways to do the same thing with too little explanation of why"* — **the direct, predicted cost of the layering philosophy**; docs are *"one huge HTML file with minimal organization"* and *"most of the docs are source code dumps of example games"*; and the shared-mutable-state hazard of a live-reloading global bag: *"something you typed in console, something that got hot-reloaded… put something weird into `args` and now it's in there until you restart."* Also: no gems at all, no `pry`/LLDB debugger, and the vendor's rebuttal to "Ruby is slow" is two YouTube comparison videos — marketing, not a benchmark.

**Agent-friendliness — and a correction.** **I could not verify that DragonRuby ships an LLM-oriented docs bundle**: `docs.dragonruby.org/llms.txt` and `/llms-full.txt` both 404, the sidebar lists no AI section, and the changelog has no AI mentions. Treat that claim as unsupported. The structural argument stands without it: Ruby's corpus is huge (2.96M repos), but DragonRuby's surface (`args.outputs.sprites <<`, `args.state`, `def tick args`, `DR.reset`, `attr_dr`, `StrictEntity`) is idiosyncratic and the runtime is explicitly *not* MRI-compatible ("DragonRuby supports a subset of MRI apis", no gems) — so a model's Ruby prior is **actively wrong**, and it will reach for gems, `require`, Gosu or Rails idioms that do not exist. This is the C3-looks-like-C trap in a different costume. Mitigating: the ~100 engine files are public and MIT, so plausibly in-corpus; and the pause/console/auto-resume loop is a near-ideal agent feedback channel. **No benchmark measuring LLM accuracy on DragonRuby exists.**

## JavaScript

**The wedge.** Distribution, uncontestably: a web game is a URL — no install, no store, no runtime download. Everything else is traded for that.

**Robustness mechanisms — mostly absent.** `undefined` and `null` are two distinct bottom values (ECMA-262 §4.4.13–14, [tc39.es/ecma262](https://tc39.es/ecma262/)); `Number` is IEEE-754 double with no integer type until `BigInt`, which hurts both determinism-sensitive gameplay and large integer IDs. `TypedArray`/`ArrayBuffer` are the numeric-density escape hatch; WebAssembly is the escape hatch for the whole language.

**GC pauses are real, and the implementers quantify them.** V8's own blog: concurrent marking "reduces the time spent marking on the main thread by 60%–70%" ([concurrent-marking](https://v8.dev/blog/concurrent-marking)); the parallel Scavenger "reduces the main thread young generation garbage collection total time by about 20%–50%" ([orinoco-parallel-scavenger](https://v8.dev/blog/orinoco-parallel-scavenger)); and the Orinoco retrospective says concurrent marking and sweeping "reduced pause times in heavy WebGL games by up to 50%" ([trash-talk](https://v8.dev/blog/trash-talk)). Earlier, V8 aimed "to keep each marking steps below 5 ms in duration" against a 16.6 ms frame budget, with full marking "potentially taking more than 100 ms for large web applications" ([free-garbage-collection](https://v8.dev/blog/free-garbage-collection)). Read as first-party admission: GC pauses in WebGL games were bad enough to justify a multi-year engineering programme, and are now *halved*, not eliminated. The community's standing mitigation is object pooling — manually defeating the GC.

**TypeScript buys less than assumed, and its maintainers say so.** The official design-goals document lists as explicit **non-goals**: *"Apply a sound or 'provably correct' type system. Instead, strike a balance between correctness and productivity"* and *"Add or rely on run-time type information in programs, or emit different code based on the results of the type system"* ([TypeScript Design Goals](https://github.com/microsoft/TypeScript/wiki/TypeScript-Design-Goals)). The handbook: *"TypeScript's type system allows certain operations that can't be known at compile-time to be safe. When a type system has this property, it is said to not be 'sound'… The places where TypeScript allows unsound behavior were carefully considered"* ([type-compatibility](https://www.typescriptlang.org/docs/handbook/type-compatibility.html)). Structural, fully erased, `any` as universal escape, no exhaustiveness unless you opt into discriminated unions and `never` tricks. **"TS-level typing" is therefore not a robustness target worth aiming at.**

**Agent-friendliness — JS is the bar.** JavaScript is the most-used language in the 2025 Stack Overflow survey at **66%** of respondents ([survey.stackoverflow.co/2025/technology](https://survey.stackoverflow.co/2025/technology)), and 45.9M GitHub repos. That translates into measured performance: on MultiPL-E, StarCoderBase-15B scored **JavaScript 31.7% pass@1 vs Rust 24.5%**, with C++ 30.6%, Java 28.5%, PHP 26.8%, Julia 21.1%, Swift 16.7%, R 10.2% ([StarCoder paper](https://arxiv.org/pdf/2305.06161), Table 2; benchmark [MultiPL-E](https://arxiv.org/abs/2208.08227)). **Caveat: 2023-era open models on HumanEval-derived toy problems — this measures "can write a small correct function", not "can write a game". Do not over-extend.**

**Complaints, and an evidence gap.** Ashley Gullen (Construct) writes candidly and at length about JS, GC and WASM at [construct.net/en/blogs/ashleys-blog-2](https://www.construct.net/en/blogs/ashleys-blog-2) — titles include "Why Javascript needs cross-heap collection" and "The case against native engines" — but **construct.net sits behind Cloudflare and refused every automated fetch (403), so I have titles and snippets only and cannot quote or verify.** Likewise, I found **no first-party Richard Davey / Phaser post** making a rigorous performance argument; the GC and object-pooling advice circulating in that ecosystem is third-party tutorial material. Both flagged as unverified.

## Rust — the robustness benchmark, and the split

The assignment was to separate the robustness that comes from the borrow checker from the robustness that comes from sum types, exhaustive matching, no-null and immutability by default. **The thesis holds up, and the two canonical first-party documents agree about which features cause pain even though they disagree about everything else.**

**The wedge.** Memory safety without a GC, enforced statically, at the cost of an ownership discipline that constrains program shape.

**Catherine West, RustConf 2018 closing keynote** ([text version by the author](https://kyren.github.io/2018/09/14/rustconf-talk.html), [video](https://www.youtube.com/watch?v=aKLntZcp27M)). Her diagnosis is entirely about **ownership**, never about types:

- The virtual-method pattern is structurally impossible — *"you will mutably borrow an Entity, and then have to mutably borrow it again to pass in a World reference"* — forcing `RefCell`, i.e. converting compile-time safety into runtime panics.
- Borrows are coarse: `world.tile(index) -> &WorldTile` borrows the *entire* world, a restriction *that would not exist with public struct fields*. **Encapsulation and the borrow checker are in direct tension.**
- From Starbound: *"every time a new requirement comes in, you have to take what may have once been sane interfaces and 'poke more holes through them'"*; *"there are many more methods than there are fields in Player, somehow."*
- Her resolution: generational indices as safe handles, struct-of-arrays components, systems as plain functions. *"Thinking about JUST the structure of state is really powerful, often times 'methods' and 'objects' get in the way."*

Read against the thesis: West's talk is a sixty-minute demonstration that **the borrow checker forbids the natural gameplay object model, and ECS is the shape you must adopt to satisfy it.** She frames that as the borrow checker teaching good design.

**LogLog Games, "Leaving Rust gamedev after 3 years"** ([loglog.games](https://loglog.games/blog/leaving-rust-gamedev/)) frames the identical observation as an unwanted tax. A two-person commercial indie team, **100k+ lines of Rust over 3 years**, shipped Steam titles, built their own 2D engine (`comfy`), left for Godot/Unity. The strongest primary postmortem that exists:

- **Borrow checker vs iteration:** it *"forces a refactor at the most inconvenient times"*; *"Being unable to just move on for now and solve my problem and fix it later was what was truly hurting my ability to write good code."* Their thesis sentence: *"I don't want 'better code', I want 'game faster' so that I can test it sooner."*
- **ECS is a workaround, not a design:** it conflates generational arenas (the part they actually needed — available standalone as `thunderdome`), composition, and data locality (rarely needed at indie scale). *"Most people using ECS are actually doing it… because it solves the particular problem of where do I put my objects."* And on culture: ECS *"has this tendency of turning from something that is considered a tool in other language to become almost a religious belief."* This is the direct rebuttal to West.
- **Abstraction tax paid in clones:** partial-borrow errors routinely worked around by cloning per frame — *"Everything now works, the borrow checker is happy, and we're cloning a string every frame."*
- **Safety promises leak:** `hecs` `query_mut` with overlapping archetypes panics at runtime during refactors, *in a codebase with no threads*.
- **Hot reload is the headline absence:** *"Hot reloading is more important for iteration speed than people give it credit for"*; `hot-lib-reloader` tried and abandoned; hot reload named as the *"#1 reason"* they would return to Unity.
- **Compile times:** ~2–5 s incremental on Linux, initially ~3× worse on Windows; proc macros destroy incrementality — one 1,600-line file of `serde`-derived structs added **+8–10 s**, forcing a separate `comfy-ldtk` crate purely to isolate monomorphisation.
- **Global-state friction:** playing a sound should be `play_sound("beep")`, not threading parameters through a dependency-injection chain.
- **Ecosystem hype over substance:** *"The Rust ecosystem lives on hype"*; *"whichever project can make the most promises, shows the best website/readme, has the flashiest gifs… gets widely praised, regardless of usability."* And: *"The community as a whole is overwhelmingly focused on tech, to the point where the 'game' part of game development is secondary."*

**And here is the split, stated by the primary source itself.** What LogLog kept liking after leaving: **generational arenas** (*"If there was one thing to point at that I like about Rust, it'd be this"*), **`Option`/`Result`** over null pointers, **sum types and exhaustive matching** (never criticised anywhere in a very long, very critical article), and fearless refactoring when the direction is already known. The cheap features survived contact. The borrow checker did not.

**Ecosystem churn, quantified.** Bevy publishes a migration guide per release and there are **16 of them, from 0.4→0.5 through 0.18→0.19**, with the project's own framing: it remains "in the experimentation phase" and "each release has its fair share of breaking changes" ([migration guides](https://bevy.org/learn/migration-guides/introduction/)). Counting entries: **0.15→0.16 has 165 distinct breaking-change entries**; **0.16→0.17 has 117**, including `Handle::Weak` replaced by `Handle::Uuid`, `Condition` renamed to `SystemCondition`, and semantics changes to `EntityRef`/`EntityMut` default query filters. At roughly three releases a year, a project tracking upstream absorbs on the order of **100–170 breaking changes per release**, and Bevy is at 0.19 with no 1.0.

**Compile times, first-party.** Bevy's official setup guide exists largely to mitigate them: dynamic linking is *"the most impactful compilation time decrease"* (explicitly not for shipping), plus `[profile.dev] opt-level = 1` with `3` for dependencies, the `lld` linker, and nightly Cranelift for *"about 30% faster"* codegen at the cost of runtime performance and macOS support ([setup](https://bevy.org/learn/quick-start/getting-started/setup/)). Note what that page does **not** contain: any absolute number.

**Correction on Embark.** Embark states *"we have used Rust as our primary programming language since the day we started the studio"* ([Inside Rust at Embark](https://medium.com/embarkstudios/inside-rust-at-embark-b82c06d1d9f4), [embark.dev](https://embark.dev/)), and rust-gpu is a concrete shipped claim — as of 0.3, all shaders for their internal engine are written in Rust ([rust-gpu](https://github.com/EmbarkStudios/rust-gpu)). **But THE FINALS runs on Unreal Engine 5.** Assert "Embark ships Rust tooling and Rust shaders, and shipped THE FINALS on UE5", not "Embark shipped THE FINALS with Rust". *(The engine-choice claim is sourced to [HN discussion](https://news.ycombinator.com/item?id=39406710), not to an Embark post — flagged.)*

**Simplicity mechanics.** Rust is the least Lua-like language here. The concept count is enormous, and the specific cliff is that ownership is not optional: you cannot write a naive first version and fix it later, which is precisely what prototyping is.

**Agent-friendliness — argue both sides.** *Against:* Rust trails JS by ~7 points pass@1 on MultiPL-E (24.5 vs 31.7). Error-mode analyses of LLM-generated Rust find `E0277` (trait not implemented) and `E0308` (mismatched types) dominating at >18% of all errors, up to 30% for some models, plus high rates of lifetime and borrow-conflict errors ([SafeTrans](https://arxiv.org/html/2505.10708v2)). *For:* the same literature shows compiler-guided repair recovers most of it — roughly **74.2% average resolution of borrow-checker violations** and ~58.7% of trait-implementation failures when diagnostics are fed back ([SafeTrans](https://arxiv.org/html/2505.10708v2)); CRUST-Bench reports borrowing errors reduced ~75% after compiler-guided repair and build-success gains up to 37% from iterative self-repair ([CRUST-Bench](https://arxiv.org/html/2504.15254v3)). **The honest reading: Rust is bad for one-shot generation and good for iterative agent loops**, because its compiler is an unusually good verifier — precise spans, stable named error codes, suggested fixes. That distinction matters enormously for a language with agents as a first-class audience.

*And a number that indicts churn directly:* RustEvo² measures LLMs against API evolution and finds **56.1% success on before-cutoff APIs versus 32.5% on after-cutoff tasks — a 23.6-point gap from API change alone** — with RAG recovering 13.5 points on average ([arXiv:2503.16922](https://arxiv.org/abs/2503.16922)). This is the quantitative backing for the Zig anecdotes above, and the strongest single argument in this survey for freezing an API early.

## The gap

**The unoccupied position is: a natively-compiled, statically-typed, non-lifetime-managed game language whose robustness comes entirely from the cheap features, whose iteration loop is DragonRuby's, and whose compiler is designed as a machine-readable verifier for an agent loop rather than as prose for a human.**

Four legs, each of which is individually occupied and none of which is occupied together.

**1. Cheap robustness without the expensive kind.** The Rust evidence splits cleanly, and both first-party sources agree on the split. West's keynote is an argument that *ownership* forbids the gameplay object model; LogLog's postmortem, after 100k lines and a decision to leave, still keeps `Option`/`Result`, sum types, exhaustive matching and generational arenas while rejecting the borrow checker for gameplay code. A language shipping **sum types + exhaustive match + no null + immutable-by-default + no implicit conversion + generational handles**, with arena/allocator discipline instead of aliasing rules, captures most of the felt robustness at a fraction of the felt cost. Odin has most of these already — but Odin's pointers are nullable, its safety story is optional-ok returns rather than non-nullability, and it explicitly declines memory safety. That is the seam.

**2. Types that are not opt-in.** The single hardest number in this survey is Roblox's: *"there is a 100x gap between the number of untyped Luau sessions and the number of typed ones"* ([arXiv:2403.02409](https://arxiv.org/pdf/2403.02409)). Gradual typing bolted onto a dynamic language does not get adopted even at Roblox's scale and with Roblox's engineering budget. And the holes are structural, not incidental: Luau is sound only over the `any`-free fragment *by its own paper*; Teal's union types are capped by what Lua's `type()` can discriminate at runtime; Nim's `not nil` is control-flow-insensitive and exception-blind by its own manual; Godot's GDScript casts silently to `null` on mismatch and keeps its type warnings **disabled by default** ([Godot docs](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/static_typing.html)). Every retrofit leaks in the same place. A greenfield, natively-compiled language pays none of these taxes — it can have real tagged sums with compiler-generated discriminants, and non-nullability in the core rather than as an experimental pass.

**3. The DragonRuby loop, in a compiled language.** The joy is mechanical and reproducible: **hot reload that preserves state** (mtime polling in the game loop, ~1 s, and critically `args.state` survives), and **errors that pause rather than crash** — in-window console, pre-filled recovery command with the RNG seed, automatic resume when you save a fix. Nobody in the compiled-static column has this. Beef is the closest and has hot reload plus a bundled debugger — and shipped nothing publicly in six years, which is the survey's most sobering datapoint. LogLog named hot reload the *"#1 reason"* they would return to Unity. Odin and Jai optimise compile speed instead, which is the same goal reached by a worse route.

**4. Agent-friendliness as a designed mechanism, not a hope.** This is the genuinely empty square. [agentlanguages.dev](https://agentlanguages.dev/) catalogues languages explicitly targeting LLM authors across three camps — syntactic (Magpie, NERD, X07, Laze), verification (MoonBit, Vera, Aver, NanoLang), orchestration (Boruna, Fabro, Lumen, Pel) — plus two systems languages, Codex and Vercel Labs' [Zero](https://github.com/vercel-labs/zero) ("The programming language for agents", Apache-2.0, `zero query`/`zero patch` over a semantic graph). **No game-oriented language appears in that catalogue.** Meanwhile Zig, the closest systems language by ambition, bans LLM contributions outright in its Code of Conduct.

But the mechanism must be honest about the ceiling. A new language starts at zero corpus, and *that gap does not close by wishing*: PyLang shows Sonnet 4.5 at **58% vs 88%** on a language absent from pretraining, and fine-tuning only narrows it to 17 points ([arXiv:2605.15607](https://arxiv.org/html/2605.15607v1)). What *did* work in that study was **idiomatic code snippets in context, worth 24 points** — far more than stating rules. RustEvo² independently shows a **23.6-point penalty for post-cutoff APIs** and 13.5 points recovered by retrieval ([arXiv:2503.16922](https://arxiv.org/abs/2503.16922)). And the Rust repair numbers show a good compiler recovers ~74% of borrow-checker violations in a feedback loop ([SafeTrans](https://arxiv.org/html/2505.10708v2)). So the agent-friendliness programme is not "be popular". It is: **freeze the surface early and never churn it; ship a canonical, idiom-dense, retrievable corpus as a first-class artefact of the language; and make diagnostics structured, stably coded and machine-repairable.** Those are engineering commitments, not syntax choices.

### What would make this language redundant

Name the neighbours honestly:

- **If it drifts toward "a nicer Odin"** — data-oriented, allocator-centric, tagged unions, `#soa`, vendored raylib — it is redundant. Odin already ships all of that, has real production users (EmberGen, LiquiGen, GeoGen; CAT & ONION; Solar Storm), and a decade of head start. Odin's unsolved problems are the *compiler and toolchain*, which is unglamorous work, not language design.
- **If it drifts toward "Lua with types"** — Luau and Teal already own it, and both have documented, structural ceilings that a compiled language would not inherit. Re-deriving those ceilings would be actively worse.
- **If it drifts toward "safe systems language"** — Rust owns it, and the survey's whole argument is that the expensive part of Rust is what makes it unsuitable for gameplay iteration. Adopting the borrow checker forfeits the wedge.
- **If it drifts toward "joyful, dynamic, fast-to-iterate"** — DragonRuby owns it and is genuinely good at it. Without static types the differentiation collapses to "DragonRuby but free and worse".
- **If it drifts toward "an agent language"** with no gamedev specificity — Zero and the agentlanguages.dev field own it, and they will out-execute a solo effort on tooling.
- **If it drifts toward "a statically-typed embeddable game scripting language"** — [Umka](https://github.com/vtereshkov/umka-lang) already exists, reached 1.0, is Go-flavoured and Lua/Wren-inspired, and drives the Tophat 2D framework. It is *embedded*, not standalone-compiled, which is the distinction to keep.
- **On the layering claim specifically**, Swift already advertises the same pitch — "approachable for newcomers and powerful for experts", scaling "from a single-line 'Hello, World!' to large-scale apps" ([swift.org/about](https://www.swift.org/about/)). "Layered" is not by itself a differentiator; the *axis* of layering is (DragonRuby layers by ceremony, not by expertise).
- **And the ambient competitor nobody in this brief listed: GDScript.** Godot ships the actual mainstream "simple, optionally-typed, gamedev-native language", with a real engine, editor and ecosystem attached. Its typing is opt-in with warnings disabled by default and a `Variant` escape hatch — precisely the leak this language would fix — but "better types than GDScript" is not, on its own, a reason for anyone to leave Godot. **The engine/ecosystem question is the existential one this survey cannot answer**, and issue #1's "spec an implementer could build from" should confront it early.

### Conflicts between the lenses, named

- **Beginner-friendly vs agent-friendly.** DragonRuby's answer to beginners is *many ways to do the same thing with intuitive transitions between them*; the documented cost, from a real user, is *"too many ways to do the same thing with too little explanation of why"*. An LLM has the same problem and worse — the PyLang finding is that models fail at *implementation fidelity*, not algorithm choice, so every additional idiomatic path is another way to be subtly wrong. **One obvious way to do it** serves agents; a ladder of ways serves beginners. These pull opposite directions and the tension must be resolved deliberately, probably by making the ladder *vertical* (each rung strictly replaces the one below, as `StrictEntity` replaces `Entity`) rather than *lateral*.
- **Simplicity vs robustness.** C3's optional/fault zoo (`?`, `!`, `??`, `!!`, plus `if (try …)`, `if (catch …)`, `@catch()`, `@ok()`) is five-plus forms for one concept. Zig's "no hidden anything" is principled and ratchets — allocators were the first threaded parameter, I/O became the second in 0.16. Every robustness mechanism costs concept count, and concept count is what "Lua-simple" spends.
- **Robustness vs iteration.** This is the Rust lesson in one line, and the reason the gap exists at all: the compile-time checks that catch bug classes are the same checks that refuse to compile a half-finished idea. A language for games has to let you be wrong on purpose, temporarily, and still run.

## Evidence quality — what is weak

Stated plainly, since the brief asked for skepticism rather than confidence:

- **Jai**: nearly everything is community reconstruction quoting an unpublished changelog. The 250k LOC/sec figure is a vendor claim, unverifiable from outside the beta. *Braid, Anniversary Edition* was **C++**, not Jai.
- **Odin**: the widely-circulated JangaFX testimonials trace to AI-generated content farms, not to JangaFX. There is no first-party "why we switched" statement.
- **Beef, C3**: no LLM evidence exists at all; both agent-friendliness assessments here are labelled speculation.
- **Nim**: the concurrency-regression specifics (threadpool deprecation, ~40% threading regression) could not be loaded and are unverified; the governance dispute is one-sided with no primary response from Araq.
- **Teal**: Hisham's three talks are vector PDFs with no extractable text — the union-restriction rationale comes from the repo docs, not the talks.
- **DragonRuby**: binary size unverified (itch.io 403); console shipping history secondary only; *A Dark Room* was RubyMotion, not GTK; **the LLM docs bundle appears not to exist** (404 on `llms.txt` and `llms-full.txt`).
- **JavaScript**: all Construct / Ashley Gullen material is behind Cloudflare and unquotable; no first-party Phaser performance writing was found.
- **Rust**: Embark's engine choice for THE FINALS is sourced to Hacker News, not to Embark.
- **Benchmarks generally**: MultiPL-E figures are 2023-era open models on toy problems. They rank languages plausibly; they do not measure game code.
- **GitHub repo counts** depend on Linguist classification; `Jai` and `C3` in particular are likely contaminated.
